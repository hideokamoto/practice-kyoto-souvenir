# 企画書: 「きょう再見」クイズ化リニューアル（仮称: 京都オープンデータ・クイズ）

作成日: 2026-10-25。根拠データは `docs/open-data-survey.md`、生成可能数は `tools/quiz-gen/poc.mjs` の実測値。

## 1. 結論（先に決めること）

- 現アプリ（観光スポット・お土産の発見/お気に入り/プラン）を、**京都市オープンデータから問題を自動生成するクイズ**に作り替える。手書き問題は作らない。データが増えれば問題が増える構造にする。
- 配信先は games.hidetaka.dev（兄弟アプリ「Anthropic数列クイズ」「京都地下鉄マニアッククイズ」と同列）。エンジンは `anthropic-version-quiz` のもの（5問1プレイ、4択、称号、ベストスコア、ja/en）を流用する。
- Phase 1（2 週間）は現リポジトリ内の 2 データセットだけで出す。追加オープンデータ（京都府観光施設一覧・Wikidata・家計調査・酒・野菜）は Phase 2 以降。**公開を先に、データ拡張は運用で**。

判断をお願いしたい点は最後（§11）にまとめた。

## 3. コンセプト

**「京都のオープンデータでつくる、毎日 5 問の京都ツウ検定」**

- 遊び方は兄弟アプリと同じ: モードを選ぶ → 5 問 → 称号つき結果 → 解説と出典リンク。1 プレイ 2 分。
- 違いは「問題がデータから自動生成される」こと。京都地下鉄クイズと同じ系譜で、題材を名所・みやげ・食・産業に広げる。
- 想定ユーザー: 京都在住者・リピーター観光客・京都検定の受験者層。現アプリのペルソナ（京都在住者）は維持する。
- 解説に必ず出典（データセット名・ファイル名・取得日）を出し、「オープンデータのショーケース」として機能させる。

## 5. 出題テンプレート（Phase 1、実測値）

`node tools/quiz-gen/poc.mjs` の出力（2026-10-25）。「生成可能数」は正解側の母集団で、ディストラクタは同カテゴリから抽選する。

### 5.1 みやげ鑑定（108 品）

| テンプレート | 問題文の型 | 生成可能数 | ディストラクタ |
|---|---|---|---|
| 説明→名前 | 「北区紫野、今宮神社の東門に面した茶店が平安後期から売る餅。……これは？」 | 108（うち 61 は説明文に名前が含まれる → `○○` にマスク） | 同じ中分類（工芸 66 / 名物 18 / 食 24）から 3 つ |
| 起源の時代・年 | 「あぶり餅が神前に供えられたのは何年？」 | 63 | 他品の年・時代 |
| 分類当て | 「『京鹿の子絞』は工芸品・名物・食のどれ？」 | 108 | 固定 3 択 |
| 読み当て | 「『洲浜』の読みは？」 | name_kana あり全件 | 似た読みを生成（要ルール設計） |

### 5.2 名所めぐり（519 事物）

| テンプレート | 生成可能数 | 備考 |
|---|---|---|
| 説明→名前 | 623 レコード（名前漏れ 288 → マスク） | 大分類（文化財/文学/食/地名・自然）内で抽選 |
| 区当て（住所から） | 154 施設（東山 33、左京 32、右京 26、上京 12、伏見 11、西京 11、北 10 …） | 南区 2・山科 2 は正解側に出さない |
| 時代当て | 148（江戸 44、平安 33、桃山 32、鎌倉 18、室町 13、南北朝 5） | 「○○時代建築の国宝建造物」等から抽出 |
| 国宝か重文か | 180 | 2 択＋「どちらでもない」で 3〜4 択 |
| 難読読み | 510 事物 | 「化野」「先斗町」「糺の森」など地名分類が強い |
| 西暦当て | 153 | 説明文中の「○○年」 |
| ジャンル当て | 名木 77 / 地名 103 / 建築意匠 47 / 狛犬 18 / 文学 72 …（元 CSV の分類コードを復元して使う） | 現 JSON には無いので `csv2json.js` を改修 |

使わないもの: 料金（84 件あるが 2021 年時点で古い）、拝観時間、建立者（正規表現では 2 件しか取れない）。

### 5.3 京都人の台所（Phase 2）
- 「2023〜2025 年平均で、京都市が 52 都市中 1 位の品目は？」正解: ヨーグルト / バター / 牛肉 / コーヒー / はくさい / きゅうり / さといも / はくさい漬 / 他の大豆製品 / 外食の和食（粗解析。正式パーサで要再検証）。ディストラクタは京都市が 20 位以下の品目。
- 「京都市のパン（支出金額）の順位は？」型の順位当て。
- 全 407 行から生成できる。数値は著作権対象外、出典記載で商用可。

### 5.4 地図・写真（Phase 2）
- 地図: 府の観光施設一覧の座標で「この地点は？」「清水寺から直線で最も近いのは？」。地理院タイルを `img-src` に追加。Ekimetry で Leaflet + 地理院タイルの実装済み。
- 写真: Wikidata P18 → Commons サムネイル。表示ごとに作者・ライセンスを出す。名寄せ済み 82 件から開始し、手作業の対応表で増やす。

## 6. 画面フロー

```
ホーム（モード一覧・ベストスコア・日替わりの有無）
  → クイズ（1/5 … 5/5。回答後に正誤・解説・出典リンク・「次へ」）
  → 結果（スコア・称号・各問の振り返り・もう一度 / 別モード / シェア文コピー）
  → クレジット（データ出典・取得日・ライセンス・加工表記、ライブラリライセンス）
```

- 兄弟アプリと同じ構成（`pages/home, quiz, result, about, licenses`）。
- 称号は京都らしい語で 6 段階（例: 全問正解「京都ツウ」〜 0 点「いちげんさん」。文言は要検討）。

## 7. 技術構成

| 層 | 方針 | 理由 |
|---|---|---|
| フレームワーク | Angular 22 standalone + signals、Ionic/NgRx/Capacitor は外す | `anthropic-version-quiz` のコード（`quiz/game.ts`, `quiz-store.ts`, `i18n`）をそのまま持ち込める。CSP `script-src 'self'` 下で実績がある |
| 問題生成 | 実行時にテンプレートから生成。`Rng` を差し替え可能にし、日替わりは日付シード | 問題をコミットしないので、データ更新＝問題更新。E2E・紹介動画撮影でシード固定できる（兄弟アプリと同じ） |
| データ | `tools/data-build/` でソース取得→正規化→`data/*.json` + `data/NOTICE.md` を生成しコミット。実行時は静的 fetch のみ（SPARQL・API を叩かない） | Ekimetry 方式。外部エンドポイントの不安定さ（今回 DBpedia 502、Wikipedia 429、京都市ポータル 503）をユーザーに波及させない |
| テスト | 生成器のプロパティテスト: 正解が 1 つだけ / 選択肢 4 つが重複しない / 問題文に正解が漏れていない / 各テンプレートの母集団が閾値以上 / 全問題に出典がある | `questions.spec.ts` の「出典必須」テストの発展形 |
| 配信 | GitHub Pages（`main` push で Actions）→ `games.hidetaka.dev/<slug>/`（`github-pages` オリジン） | AWS 費用ゼロ、兄弟アプリと同一手順。`cdk/src/apps.ts` に 1 要素追加 |
| CSP 緩和 | Phase 1: `style-src 'unsafe-inline'` のみ。Phase 2: `img-src` に `upload.wikimedia.org`, `cyberjapandata.gsi.go.jp` | ポータルの allowlist 範囲内 |
| 計測 | 外部タグは置けない。GitHub Pages 側のログも無い | KPI はシェア文コピー数等のクライアント内指標か、ポータル側 CloudFront ログに頼る（要相談） |

## 8. 出典・ライセンスの設計

- `data/NOTICE.md` にソースごとの名称・URL・ライセンス・取得日・加工内容を書き、クレジット画面に同じ内容を表示する。
- 京都市データ: 「出典: 京都市オープンデータポータルサイト『京都観光Navi』（京都市）を加工して作成」。**規約原文の指定文言はポータル復旧後に確認して差し替える**。
- 家計調査: 「『家計調査結果』（総務省統計局）を加工して作成」（e-Stat 利用規約の例に従う）。
- Wikidata: CC0 だが Wikidata 由来と明記。Commons 画像はファイルごとの作者・ライセンスを画像下に表示。
- 文化庁 DB: 文字情報のみ使用、画像は使わない。
- 現アプリのように出典無しで公開しない。これは Phase 1 の受け入れ条件に入れる。

## 9. リスクと対策

| リスク | 対策 |
|---|---|
| 京都市ポータルが長期停止し、規約原文が確認できない | BODIK 掲載の CC BY 4.0 表記と Wayback スナップショットを根拠にしつつ、クレジットに「規約確認日」を書く。復旧後に差し替え |
| 「京都観光Navi」が 2021 年で更新停止している | 料金・時間など時変情報を出題しない。説明文・読み・時代・区は陳腐化しにくい |
| 説明文からの名前当てで答えが漏れる（288/623） | マスク処理＋テストで「正解文字列が問題文に含まれない」を強制 |
| 読み当てのディストラクタが不自然 | 同じ文字数・同じ頭文字の他エントリの読みを優先し、無ければそのテンプレートを出さない（母集団閾値テスト） |
| Wikidata/Commons 画像の権利表記漏れ | 画像メタデータ（作者・ライセンス）をビルド時に取得できないものは採用しない |
| 既存の「京都地下鉄マニアッククイズ」と被る | 地下鉄駅情報は使わない。将来、両アプリの日替わりを横断させる案は別検討 |

## 11. 判断をお願いしたい点

1. **アプリ名と slug**: 候補「京都オープンデータ・クイズ」「きょう再見クイズ」「京みやげ鑑定」。slug 案 `kyoto-quiz` / `kyoto-miyage-quiz`（`^[a-z0-9][a-z0-9-]{1,62}$`、予約語不可）。
2. **Ionic / Capacitor の撤去**: ストア配信の予定が無ければ外す提案。残す場合は CSP 下での動作確認工程を週 1 に追加する。
3. **リポジトリ**: このリポジトリを書き換える（履歴とデータ変換スクリプトを継承）か、新規リポジトリにするか。提案は前者。
4. **Phase 1 の範囲**: 上記 2 モード・7 テンプレートで出すことで良いか。削るなら「読み当て」（ディストラクタ設計に時間がかかる）。
5. **家計調査モードの命名と注記**: 「京都人の台所」。2 人以上の世帯・3 年平均の注記をどこまで出すか。
